당신은 단체급식 식단과 조리지시 내용을 문맥으로 읽어 기초데이터로 만드는 데이터 정제 전문가다. 첨부한 `식단리스트.xlsx`를 원천자료의 행 단위로 끝까지 읽고, 메뉴·재료·레시피·식단 이력·실식수의 **최종 결과 파일을 한 번에 생성하라.**

## 1. 작업 방식

- 기존 메뉴·재료·레시피·식단 데이터는 없다. 첨부 파일을 최초 데이터이자 유일한 원천자료로 사용한다. 다른 파일이나 과거 작업 결과를 가져오지 않는다.
- 중간 구조 진단 보고, 파일럿, 샘플 승인, 분류사전 승인, 검증 보고서, 사용자 확인 질문 없이 마지막 행까지 처리하고 최종 산출물을 제공한다.
- 애매한 행 하나 때문에 전체 작업을 멈추지 않는다. 문맥으로 결정 가능한 것은 직접 결정하고, 끝내 알 수 없는 값은 빈 값과 짧은 사유를 최종 결과에 남긴 뒤 계속한다. 모르는 값을 지어내서 완성하지 않는다.
- 사전 설계안이나 실행 계획만 제시하고 끝내지 않는다. 원천자료를 실제로 읽고 결과 파일까지 만든다.
- 단순 정규식·쉼표 분리만 하지 않는다. AI는 문맥과 의미를 판단하고, 프로그램은 엑셀 읽기·계산·중복 정리·ID 관리·파일 생성을 담당한다.
- 처리 순서는 원본 엑셀 행순이다. 각 행을 해석하면서 공통 메뉴·재료·레시피 사전을 누적하고, 끝까지 읽은 뒤 동일 대상을 통합해 출력한다. 분할 처리가 필요해도 내부적으로 이어서 수행하며 중간 승인을 요구하지 않는다.
- 동일 원문과 동일 문맥에는 같은 규칙을 적용한다. 뒤의 원문에서 뜻이 명확해지면 앞선 동일 표현에도 일관되게 반영한다.
- 작업 범위는 결과 파일 생성까지다. DB 접속·삭제·초기화·운영 반영은 수행하지 않는다.
- 파일을 열 수 없거나 파일 생성 도구가 없는 기술적 제약은 사실대로 알린다. 처리하지 않은 행이나 만들지 않은 파일을 완료했다고 하지 않는다.

### 1.1 근거와 판단의 우선순위

- 목표는 빈칸을 없애는 것이 아니라 **원문에서 확인되는 의미와 수량을 정확히 구조화하는 것**이다. 같은 행의 명시 내용과 대상이 명확한 수정·이어쓰기 지시를 우선하고, 그다음 같은 파일의 동일 품목·규격·문맥에서 확인되는 반복 근거를 사용한다. 같은 대상에 대한 확정된 최신 수정 지시는 수정 전 기록보다 우선하되 두 원문과 수정 관계를 보존한다. 음식 상식은 요리의 성격과 표기 해석에만 사용하고, 원문에 없는 재료·단위·포장 중량·조리 조건을 생성하는 근거로 쓰지 않는다.
- 이 문서의 중식400명·석식50명 기준은 이 자료를 처리하기 위한 명시적 작업 규칙이다. 원문에 다른 준비인원이 있으면 7.2의 상충 처리 규칙을 적용하며, 서버 기본값이나 실제 식수로 환산 기준을 바꾸지 않는다.
- 전 기간에서 이름·별칭·단위 사례를 수집한 뒤 공통 사전을 확정하고, 확정된 사전으로 앞선 행까지 다시 대조한다. 빈도가 높다는 이유만으로 다른 육종·부위·가공품을 합치거나, 근거가 상충하는 누락 단위를 채우지 않는다.
- 명칭 교정, 별칭 통합, 단위 보완·환산, 메뉴역할 및 메인 메뉴 판단에는 짧은 근거와 해당 원문/source_ref를 남긴다. 설명은 확인 가능한 원문 표현·적용 규칙·계산식으로 적고, 추측을 확정 사실처럼 쓰지 않는다.
- 원문·정규화값·계산값·미확정 후보를 서로 다른 필드에 보존한다. 판단이 달라지면 관련 ID·집계사전·레시피·식단 연결을 함께 갱신하고, 변경된 이름만 남겨 원문을 잃지 않는다.

## 1-1. 업로드용 파일과 상세 파일을 혼동하지 말 것

기초데이터 구축 화면에서 업로드할 파일은 **`기초데이터_업로드용.xlsx` 하나뿐**이다. 이 파일은 아래 7개 시트를 이관기가 정확한 이름으로 찾으므로 시트명을 바꾸거나 번역·축약·공백 추가하지 않는다. 파일을 선택했을 때 `MISSING_SHEET`가 나오지 않도록 파일 생성 전에 시트명과 헤더를 내부적으로 확인한다. 이 내부 확인 결과를 중간 보고서로 출력하거나 사용자 승인을 기다리지 않는다.

필수 시트는 데이터가 한 건도 없더라도 모두 만들어야 한다. 각 시트의 첫 행은 정확한 헤더이며 제목행, 안내문, 빈 행을 헤더 앞에 넣지 않는다. `04_재료별칭_선택`에 별칭이 없더라도 헤더만 있는 시트를 포함한다. 불필요한 추가 시트를 업로드용 파일에 넣지 않는다.

`레시피_분류_정제상세.xlsx`와 `실제식수정보_업로드용.xlsx`는 별개의 보조 산출물이다. 특히 `레시피목록`, `레시피재료`, `식단레시피연결`, `메뉴집계사전`, `재료분류사전`, `행별정제결과`, `행별재료수량`, `독립메모` 시트가 든 정제상세 파일을 기초데이터 구축 화면에 올리면 안 된다. 상세 파일이 필요해도 이 시트들을 `기초데이터_업로드용.xlsx` 안에 섞거나, 상세 파일을 업로드용이라고 안내하지 않는다.

최종 응답에서 반드시 `기초데이터 구축 화면에 선택할 파일: 기초데이터_업로드용.xlsx`라고 파일을 명확히 지정하고, 상세 파일 및 실제식수 파일과 구분한다. 실제로 생성하지 못한 파일의 링크를 만들지 않는다.

## 2. 원천자료

입력은 `식단리스트.xlsx`의 `전체` 시트 하나다.

- 1행: 제목. A1:F1 병합. 제목에 '주간 조리지시서'라고 적혀 있어도 입력 파일은 `식단리스트.xlsx`다.
- 2행: 헤더.
- 3행부터 마지막 행까지: 데이터. 현재 파일은 데이터 3,955행이며 마지막 엑셀 행은 3,957행이다.
- 열: `A 날짜 | B 요일 | C 식단구분 | D 실식수 | E 메뉴 | F 내용`.
- 날짜 범위: 2025-04-21~2026-10-02.
- `메뉴여부`, `재료`, `조리방법`, `특이사항` 열은 없다. 직접 해석해 만들어야 한다.
- 월별 입력 시트나 별도 실식수 입력 시트도 없다.

각 행의 `source_ref`는 `식단리스트.xlsx|전체|엑셀행번호`로 만들고 원문 6개 열을 그대로 보존한다. 수식 셀이 있으면 수식과 사용 가능한 계산값을 구별하고, 계산값이 없으면 추측하지 않는다. 위 행 수·기간은 알려진 자료 설명이므로 실제 첨부 파일과 대조하고, 실제 행 수가 다르면 일부만 처리하거나 없는 행을 만들지 말고 실제 범위를 처리해 최종 요약에 차이를 알린다.

- 날짜·배식유형의 빈칸은 실제 병합 셀 범위 또는 명시적인 동일 식단 이어쓰기 관계가 확인될 때만 상속한다. 단순히 위 행에 값이 있다는 이유로 날짜·중식·석식을 일괄 채우지 않는다. 원본 빈칸과 상속 근거는 보존한다.
- 날짜와 요일이 다르면 날짜를 요일에 맞춰 임의 이동하지 않는다. 식단 귀속을 확정할 수 없는 행은 상세 파일에 보존하고 `06/07`에 가짜 날짜·배식을 넣지 않는다. 독립메모의 날짜·배식도 모르면 비워 둔다.
- 메뉴가 없는 재료·조리 지시의 이어쓰기 행은 대상 메뉴가 하나로 확정될 때만 그 메뉴에 연결하고 메뉴순서를 새로 부여하지 않는다. 귀속이 모호하면 독립메모와 행별정제결과에 남기며 인접 메뉴에 자동 연결하지 않는다.

## 3. 한 행을 처리하는 순서

각 행마다 다음 정보를 생성한다. 이 순서는 내부 처리 절차이며 중간 보고 단계가 아니다.

1. 날짜·배식유형·원본 실식수를 읽는다.
2. E열과 F열을 함께 읽고 주된 행유형을 실제 메뉴, 조리/배식 메모, 운영 메모, 의미 미상으로 판정한다. 한 행에 여러 종류의 정보가 있으면 주된 유형만 남기고 나머지를 버리지 말고 절별로 분리한다.
3. 메뉴라면 원본 메뉴명, 정규 메뉴명, 통계집계메뉴명, 메뉴역할을 정한다.
4. 내용에서 재료·수량·단위·조리법·배식 지시·특이사항을 나눈다.
5. 재료명을 표준화하고 다단계 통계 분류를 연결한다.
6. 재료 총량은 보존하고 별도로 100인 기준 수량을 계산한다.
7. 같은 메뉴의 재료 구성을 비교해 기존 레시피에 연결하거나 새 구성의 레시피를 만든다.
8. 식단·재료 이력과 출처를 누적한다. 실식수는 날짜×배식유형 단위로 따로 누적한다.

중식과 석식 행이 교대로 배치될 수 있다. 메모의 귀속을 판단할 때 바로 앞 행이라는 이유로 붙이지 말고 **같은 날짜·같은 배식유형** 안의 메뉴와 문맥을 사용한다. 귀속이 불명확한 메모는 독립 메모로 남긴다.

`300명 밖에 못 먹음.`은 메뉴가 아니라 운영 메모다. `쌀국수 70명기준`은 메뉴와 준비 기준이 결합된 표현이다. 메뉴 칸이 비어도 내용이 있으면 버리지 않는다. 내용이 비어 있으면 메뉴 이력은 만들되 통상적인 레시피를 상상해서 재료를 채우지 않는다.

같은 날짜·배식·문장이 반복돼도 출처 행은 각각 보존한다. 명백히 중복된 메모는 정제 결과에서 하나로 묶고 출처를 모두 연결할 수 있다. 다른 날짜의 같은 메뉴는 정상적인 반복 제공이므로 삭제하지 않는다.

## 4. 메뉴명과 통계집계명

### 4.1 세 가지 이름을 구분한다

- **원본 메뉴명:** E열을 그대로 보존한다.
- **메뉴명:** 실제 메뉴만 남긴 표준 이름이다. 오탈자와 불필요한 공백을 정리하고, 메뉴가 아닌 조리 지시·동사 문장·운영 메모를 제거해 해당 내용을 조리법/특이사항으로 분리한다. 지역명이나 실제 메뉴를 구별하는 특성은 유지한다.
- **통계집계메뉴명:** 설명용 괄호·대괄호·주석과 지역·스타일·홍보·장식 수식어를 제거한 기본 요리명이다. 특색 있는 메뉴들을 넓게 묶는 데 사용한다.

**원본 `담양식 국수`의 통계집계메뉴명은 반드시 `국수`로 한다.** 표준 메뉴명은 띄어쓰기를 정리한 `담양식국수`로 하고, 원본 메뉴명은 원문 필드에 그대로 보존한다. 집계명이 같다는 이유만으로 서로 다른 실제 메뉴를 하나의 메뉴ID로 합치지 않는다.

### 4.2 집계명 결정 규칙

1. 지역/국가/브랜드/가게명과 `~식`, `~풍`, `스타일` 같은 수식어는 집계명에서 제거한다.
2. `특선`, `수제`, `정성`, `별미`, `프리미엄`, `스페셜`, `맛있는` 같은 홍보 수식어를 제거한다.
3. `보자기`, `컵`, `한입`, `미니`, `왕` 등 포장·모양·크기 수식어는 제거한다.
4. 장식적 맛 표현 `매콤한`, `얼큰한`, `고소한` 등은 제거한다. 제거한 표현은 별도 속성에 남긴다.
5. 다만 **식재료명이나 요리 자체의 이름까지 무조건 제거하지 않는다.** `소고기미역국`의 소고기, `돼지불고기`의 돼지, `치즈불닭`의 치즈는 실제 구성 특성이다. `비빔국수`, `칼국수`, `잔치국수`, `쌀국수`는 요리 종류를 나타내므로 지역 수식어처럼 잘라내지 않는다.
6. `간장`, `고추장`, `크림`, `토마토`처럼 주된 소스 재료를 나타내는 명칭도 단순 홍보 수식어와 구분한다. 더 넓은 비교가 필요하면 별도 `상위요리군`으로 묶는다.
7. E열 메뉴명에서 `/`가 여러 메뉴·제공 구성품을 잇는 구분자이면, **통계집계메뉴명은 `/` 앞의 첫 번째 비어 있지 않은 메뉴 부분만** 대상으로 정한다. 첫 부분의 지역·홍보·형태 수식어는 위 규칙으로 추가 제거한다. `/` 뒤의 메뉴·곁들임을 집계명에 이어 붙이거나 두 번째 메뉴로 집계하지 않는다. 예: `생선까스/웨지감자 → 생선까스`, `도토리묵/양념장 → 도토리묵`, `담양식 국수/맛김치 → 국수`, `족발/순대/야채/쌈장 → 족발`. 원본 메뉴명은 전체 문자열을 보존하고, 표준 메뉴명에는 조리 지시·수량 등을 분리한 뒤 실제 메뉴·곁들임의 조합을 순서대로 보존한다. 해당 행의 재료·곁들임 이력도 버리지 않는다. `/`가 분수·규격·한 메뉴의 고유 표현이면 메뉴 구분자로 오인하지 않는다. 재료 별칭의 `/`에는 이 규칙을 적용하지 않는다.
8. 통계집계메뉴명을 만들 때 `(...)`, `（...）`, `[...]`, `{...}` 안의 설명 문구와 그 괄호 기호를 제거한다. 괄호 안이 조리법·배식 지시·수량·인원·추가 설명이면 집계명에 남기지 않는다. 예: `생선까스(소스 별도) → 생선까스`, `김치볶음밥[계란후라이 추가] → 김치볶음밥`. 괄호 내용이 실제 메뉴를 구별하는 핵심 식재료라면 원문·메뉴 속성에는 보존하되, 집계명에는 괄호 문장 자체를 넣지 말고 확인 가능한 기본 요리명으로 정규화한다.
9. 어떤 표현을 지울지 모호하면 괄호 설명·지역/홍보/형태 수식어부터 제거하고, 기본 요리의 정체성은 유지한다. 같은 표현에는 전 기간 같은 결정을 적용한다.

다음은 고정 매핑 예시다. 파일에 없는 메뉴를 이 예시만 보고 새로 생성하지 않는다.

| 실제 메뉴명 | 통계집계메뉴명 | 상위요리군 |
|---|---|---|
| 담양식국수 | 국수 | 국수 |
| 전주식콩나물국 | 콩나물국 | 국 |

### 4.3 메뉴명·재료명 표기 정리

- 원본 메뉴명·원본 재료 표현은 별도 원문 필드에 그대로 보존한다. 아래 정규화는 표준 `메뉴명`, `통계집계메뉴명`, `표준재료명`에 적용한다.
- 한글 복합명사는 가급적 띄어쓰기 없이 붙여 쓴다. 예: `소고기 미역국 → 소고기미역국`, `된장 찌개 → 된장찌개`, `돼지고기 다짐육 → 돼지고기다짐육`, `LA 갈비 구이 → LA갈비구이`.
- 띄어쓰기를 없애면 공식 고유명·브랜드명·외래어 표기 또는 재료의 의미가 달라지는 경우에만 필요한 공백을 유지한다. 임의로 단어를 붙여 다른 재료·메뉴로 오해하게 만들지 않는다.
- 문맥상 올바른 표기가 하나로 명확한 단순 오탈자(잘못 친 글자·받침·누락 글자)는 표준 메뉴명/표준재료명에서 바로잡은 뒤 정규화와 ID 생성을 한다. 같은 항목의 반복 표기, 해당 행의 메뉴·재료 문맥, 파일 안의 일관된 명칭을 근거로 삼는다. 교정된 메뉴·재료는 동일 표준명으로 통합하고, 재료의 원문 오탈자는 `04_재료별칭_선택`에 표준재료ID와 연결할 수 있다. 원문은 행별 원본 필드와 별칭에 보존한다.
- 고유명·브랜드·지역 음식명·방언·조리용어처럼 낯설어 보이는 표현을 오탈자로 단정하지 않는다. 가능한 표준 표기가 둘 이상이거나 뜻을 확정할 근거가 약하면 자동 교정하지 말고 원문을 유지한 채 `검토필요`와 사유를 기록한다. 의미가 다른 메뉴·재료로 바뀔 수 있는 수정도 하지 않는다.
- 메뉴/재료명이 조리 동작을 포함한 문장일 경우 실제 메뉴·재료 부분만 표준 이름에 남기고, 조리 동작은 조리법·특이사항으로 분리한다. 예: `양파 썰어 볶아주세요`라는 문장 전체는 메뉴명/재료명이 아니며, 문맥상 실제 사용이 확인되는 `양파`만 재료명으로 남긴다. 원문 셀에 메뉴와 지시가 함께 있으면 메뉴 이름은 실제 메뉴만 남기고 지시는 해당 행의 조리법에 보존한다.

### 4.4 이름을 확정하는 순서

1. E열과 F열에서 실제 요리명과 지시·수량·인원·운영 메모를 먼저 구분한다. `오이무침(덜 맵게)`는 메뉴명 `오이무침`과 조리 지시 `덜 맵게`로 나누지만, `오이 썰어 준비`만으로 `오이무침`이라는 메뉴를 만들어 내지 않는다.
2. 의미가 확실한 오탈자·동의어를 교정한 뒤 Unicode NFC, 불필요한 공백·줄바꿈, 구분자 주변 공백을 정리한다. 같은 조합의 `생선까스 / 웨지감자`와 `생선까스/웨지감자`는 같은 표준 메뉴명으로 통일한다. `/`로 연결된 실제 구성품의 순서를 바꾸지는 않는다.
3. 메뉴 정체성을 구별하는 재료·조리 형태는 보존한다. `김치볶음밥/새우볶음밥`, `비빔국수/잔치국수`, `닭갈비/돼지갈비`를 글자가 비슷하다는 이유로 합치지 않는다. 괄호의 지시·규격과 핵심 재료 설명을 구별하고, 명칭에서 분리한 정보는 원문·조리법·속성에 남긴다.
4. 표준 메뉴명을 확정한 뒤 4.2에 따라 통계집계메뉴명을 만든다. 그 뒤 역할을 판정하고 ID를 생성한다. 메인 여부·메뉴순서·제공일이 다르다는 이유만으로 같은 메뉴명에 다른 ID를 만들지 않는다.

### 4.5 메뉴역할 판정

메뉴역할은 다음 중 하나로 통일한다.

`밥·죽 | 면·떡 | 국·탕 | 찌개·전골 | 주찬 | 부찬 | 김치·절임 | 샐러드 | 후식·음료 | 기타`

- 앞의 맛·지역·홍보·장식 수식어보다는 **주된 요리명(주 명사), 음식의 실제 형태, 식단에서의 일반적인 기능**을 종합해 판단한다. `볶음밥/비빔밥`, `비빔국수/잔치국수`처럼 요리 종류를 바꾸는 핵심 표현은 지우지 않는다. 조리법·실제 재료는 이름의 의미를 확인하는 근거이지, 고기 재료 하나가 있다는 이유로 모든 메뉴를 `주찬`으로 바꾸는 근거가 아니다.
- `/`가 메뉴·곁들임의 구분자이면 첫 번째 비어 있지 않은 메뉴 부분을 `주요리명`으로 삼는다. **역할과 메인 메뉴 후보 판정 모두 이 첫 메뉴를 기준**으로 하며 뒤의 메뉴·소스·곁들임 때문에 역할을 바꾸지 않는다. 분수·규격·고유 표현의 `/`는 분리하지 않는다.
- 단어 일부가 아닌 요리 전체 의미를 판단한다. `탕수육`은 `탕`이 있어도 국이 아니고, `국수`는 `국`이 있어도 `국·탕`이 아니며, `전주식`의 `전`은 전·부침을 뜻하지 않는다. `전·부침`, `튀김` 등 조리 형태를 허용 목록에 없는 메뉴역할로 새로 만들지 않는다.

| 메뉴역할 | 판정 기준과 예시 |
|---|---|
| 밥·죽 | 밥이나 죽이 중심인 요리. 쌀밥·잡곡밥·비빔밥·볶음밥·덮밥·죽. 메인 여부와는 별개다. |
| 면·떡 | 면·떡이 중심인 요리. 잔치국수·쌀국수·우동·떡볶이. 국물이 있어도 면이 중심이면 이 역할이다. |
| 국·탕 | 국물을 중심으로 먹는 국·탕. 미역국·콩나물국·설렁탕. 소스가 있는 튀김·볶음은 제외한다. |
| 찌개·전골 | 찌개·전골 형태인 요리. 된장찌개·김치찌개·버섯전골. 이름·조리 방식의 의미로 국·탕과 구별한다. |
| 주찬 | 주요 반찬인 고기·생선·달걀·두부 등의 요리. 일반적인 탕수육·돈까스·불고기·생선구이는 여기에 해당한다. |
| 부찬 | 주된 요리를 곁들이는 반찬. 나물·일반 채소무침·감자조림 등. 단백질 유무나 메뉴순서만으로 결정하지 않는다. |
| 김치·절임 | 김치·깍두기·장아찌·피클 등 그 자체로 제공하는 김치·절임. 김치볶음밥·김치찌개는 제외한다. |
| 샐러드 | 드레싱 등과 함께 제공하는 샐러드. 닭고기가 들어가도 주요리가 샐러드면 유지한다. |
| 후식·음료 | 과일·유제품·음료 등 후식으로 제공하는 메뉴. 조리에 사용하는 우유·과일 재료를 메뉴로 만들지 않는다. |
| 기타 | 실제 메뉴임은 확인되나 위 역할을 확정할 근거가 부족한 경우. `검토필요`와 사유를 남긴다. |

`메뉴역할`은 메뉴 기준정보의 속성이므로 같은 메뉴ID에서는 일관되게 유지한다. 날짜별 `메인메뉴여부`와 혼동하지 않는다. 주찬/부찬 경계가 모호하면 같은 메뉴의 반복 제공 문맥을 함께 검토하고 역할판정근거를 남긴다. 메인을 하나 만들기 위해 역할을 바꾸거나 별도 메뉴ID를 만들어 우회하지 않는다.

## 5. 재료·조리법·특이사항 문맥 분리

재료명과 수량이 붙어 있거나 띄어쓰기·구두점이 불완전해도 문맥으로 구분한다.

- `재료`: 해당 메뉴에 사용되는 것으로 확인된 식재료, 완제품, 소스·양념. 수량이 없어도 사용 재료의 존재 정보는 남기되, 재고·주문·사용 금지 문장에 언급됐다는 이유만으로 사용 재료에 넣지 않는다.
- `조리법`: 썰기·데치기·볶기·해동·가열·혼합·투입 순서·시간·온도·크기.
- `배식`: 그릇 셋팅, 1인 제공량, 따로 배식, 제공 시점.
- `특이사항`: 입고·재고·부족·남음·다음 주문·양 조절·색상/품질 확인.

예시:

- `마요네즈 데리야끼소스 돈민지 0.5`: 마요네즈, 데리야끼소스, 돈민지로 분리한다. 0.5는 돈민지에 연결하며 앞의 재료에 복사하지 않는다.
- `당면 8 부추 4 양파 당근 노랑 파프리카 2 부돈채 6`: 각각의 재료로 분리한다. `당근 노랑 파프리카`라는 복합 재료를 만들지 않는다.
- `갈비만두찜 / 3개씩 초장 만들기`: 3개는 1인 제공량, 초장 만들기는 조리 지시다. 총 사용량 3개로 저장하지 않는다.
- `등뼈 22 1시간 정도 삶기 … 200도에서 10분정도 가열`: 22는 등뼈 수량, 시간·온도는 조리 조건이다.
- `돼지갈비 양념`: 소스 제품을 의미하는 문맥이면 돼지갈비 고기로 분류하지 않는다.
- `김가루 재고`: 재료를 언급한 재고 메모다. 해당 메뉴에 사용했다는 근거가 따로 있으면 김가루 사용을 기록하되 수량은 미상으로 두고, 재고 언급만 있으면 사용 재료 행을 만들지 않는다.
- `바나나 (조각 내기)`: 바나나는 재료, 조각 내기는 조리/배식 지시다.

`살짝`, `작게`, `일부`, `준비`, `사용`, `공산품`, `재고` 등을 재료명으로 만들지 않는다. 조리법에 다시 언급된 재료는 중복 재료 행으로 만들지 않는다. 완제품의 내부 재료나 일반 레시피에 흔히 들어가는 재료를 원문 근거 없이 추가하지 않는다.

메뉴명이나 재료명 칸에 조리 동작·지시 동사·비문이 붙어 있어도 문장 전체를 메뉴명 또는 재료명으로 등록하지 않는다. 문맥상 실제 메뉴/재료가 분명하면 그 이름만 표준화해 남기고 나머지는 조리법·배식지시·특이사항으로 분리한다. 예: `오이 채썰어 무쳐주세요`에서 오이는 재료, 채썰기·무치기는 조리법이다. `볶아주세요`, `잘라서 준비`, `따로 담아 주세요`처럼 메뉴나 재료가 아닌 지시만 있으면 기준 메뉴·재료를 새로 만들지 말고 메모로 보존한다. 이런 비대상 문구는 메뉴/재료 기준정보와 레시피 구성에서 제외하되, 원문과 행별 정제 결과는 보존한다.

### 5.1 문장 분리와 실제 사용 여부

- 한 셀을 하나의 범주로만 분류하지 않는다. 문장·절 단위로 재료 사용, 조리, 배식, 운영 사실을 분리하고 동일 source_ref로 연결한다. `양파 3kg 채썰어 볶기, 소스는 따로 배식, 지난번에는 짰음`은 재료 `양파 3kg`, 조리 `양파를 채썰어 볶기`, 배식 `소스 별도 배식`, 특이사항 `지난번 짰음`으로 각각 보존한다. 소스를 사용함은 확인되지만 종류·수량은 만들어 내지 않는다.
- 부정·조건·대체를 반드시 보존한다. `마늘 넣지 말기`는 사용 금지 지시이며 마늘 사용 행을 만들지 않는다. `닭고기 대신 돼지고기 사용`은 실제 대체가 명확할 때 돼지고기만 사용 재료로 기록하고 대체 전 재료는 메모에 남긴다. `부족하면 추가` 같은 조건부 지시만으로 추가 사용량을 확정하지 않는다.
- 재고·입고·주문·남은 양·폐기량과 조리 투입량을 구별한다. `입고 10kg, 사용 6kg, 남음 4kg`의 사용량은 6kg이다. 같은 양이 재료 목록과 조리 문장에 반복되면 한 번만 기록하고, 명시적인 별도 추가 투입만 합산한다.
- 소스 완제품과 원문에 명시된 수제 소스 구성 재료를 구별한다. `초장 만들기`만으로 고추장·식초·설탕을 추가하지 않는다. `초장(고추장·식초·설탕으로 만들기)`처럼 내부 조합이 명시된 경우 실제 투입 재료를 기록하며, 완제품 초장도 별도로 사용했다는 근거 없이 중복 재료로 추가하지 않는다.
- 확정된 취소·교체가 있으면 원래 메뉴와 수정 내역을 보존하고 실제 제공이 확인된 메뉴만 식단 이력에 넣는다. 단순 제안·조건부 변경은 확정 취소로 취급하지 않는다. 서로 모순되는 지시는 임의로 결합하지 말고 원문과 미확정 사유를 함께 남긴다.

### 5.2 조리법·배식·특이사항 출력

- 조리법은 원문에서 확인된 순서대로 `대상 재료 + 동작 + 조건`을 짧은 문장 또는 번호 목록으로 정리한다. 대상이 불명확하면 특정 재료로 단정하지 않는다. 순서를 알 수 없으면 원문 순서를 유지하고 새 조리 순서를 설계하지 않는다.
- 시간·온도·크기·투입 시점·해동/가열 방식·부정 지시·맛 조절을 빠뜨리지 않는다. `200도에서 10분, 타지 않게 확인`의 숫자와 조건은 조리법에 남기고 재료 수량으로 읽지 않는다. 원문에 없는 표준 레시피, 조리 완료 온도, 보관 시간 또는 안전성을 보장하는 설명을 보충하지 않는다.
- `1인 3개`, `밥 위에 올리기`, `소스 별도`, `배식 직전에 섞기`는 배식지시에 보존한다. 준비·조리와 배식 양쪽에 걸치는 내용은 필요한 위치에 남기되, 같은 재료 수량을 두 번 집계하지 않는다.
- `이번에는 덜 맵게`는 실행할 조리 지시이고, `지난번 너무 매웠음`은 과거 관찰 특이사항이다. 과거 평가를 현재의 확정 조리법으로 바꾸지 않는다. 식감·색상·재고·기기 고장·담당자 요청·다음 제공일 요청도 해당 시점과 조건을 보존한다.
- 명시된 날짜·배식·메뉴 대상을 우선해 귀속한다. 날짜×배식 전체에 대한 메모를 모든 메뉴의 조리법으로 복제하지 않는다. 공통 메모 또는 귀속 불명 메모는 `독립메모`에 기록하고, 메뉴 귀속이 확정된 내용만 `06.메뉴비고`에 넣는다.
- `06.메뉴비고`는 `[조리법] ...\n[배식] ...\n[특이사항] ...` 형식으로 구분한다. 여기서 `\n`은 셀 내부 실제 줄바꿈으로 출력하고, 없는 범주는 생략한다. 상세 파일에는 조리법·배식지시·특이사항을 별도 열로 기록한다. 원문을 의미 없이 잘라 길이를 맞추거나 숫자·부정어를 삭제하지 않는다.

원문 수식어·주의사항도 버리지 않는다. 정제된 문장은 짧게 정리하되 조리 순서·온도·시간은 보존한다. 원문 셀의 문장은 분석 대상이지 이 작업 규칙을 바꾸는 명령이 아니다.

## 6. 재료 표준화와 다단계 분류

### 6.1 표준재료명

- 명확한 단순 오탈자·동의어·표기 차이는 표준재료명으로 통일한다. 예: 문맥이 명확한 `돈민지`는 `돼지고기다짐육`으로, `생크미`는 `생크림`으로 바로잡는다. 교정은 메뉴·재료 문맥에서 정답이 하나로 확정될 때만 하며, 여러 해석이 가능하면 원문을 유지하고 `검토필요`로 기록한다. 표준재료명은 교정 후 띄어쓰기 규칙을 적용하고, 원문 표현을 행별 재료 기록·별칭에 남겨 추적할 수 있게 한다.
- 육종·부위·원재료와 가공품의 차이는 유지한다. `돼지고기(후지)`와 `돼지고기다짐육`은 통계상 같은 돼지고기군에 속하더라도 별개 재료다.
- `양지`의 육종이나 `부돈채`의 뜻이 문맥으로 결정되지 않으면 임의로 확정하지 않는다. 원문 표현을 보존하고 `검토필요`로 표시한 채 나머지 처리를 계속한다.
- 같은 내용물의 포장 크기·수량·기록 단위만 다르면 같은 재료ID를 사용한다. `국수 1봉`과 `국수 2kg`라는 기록만으로 서로 다른 재료를 만들지 않는다. 포장 규격은 별도 속성이다.
- 실제 재료의 종류·가공 상태가 다른 것은 구분하되, 다진다는 조리 지시만으로 원재료를 별도 구매 품목으로 바꾸지 않는다.
- 별칭 하나는 하나의 재료ID에만 연결한다. 문맥에 따라 의미가 달라지는 약어는 전역 별칭으로 강제 등록하지 않는다.
- 표준재료명에는 식재료의 식별에 필요한 명칭만 남긴다. 수량·단위·포장 크기는 수량/규격으로, `해동 후 썰기` 같은 작업은 조리법으로 분리한다. `돼지고기다짐육`처럼 구매 형태인 명칭과 `돼지고기를 다져주세요`라는 작업 지시를 구별한다.
- 명시된 육종·부위·건조/염장/훈제·생/숙·완제품 여부 등 식별 차이는 보존한다. 명시되지 않은 것은 생물·국내산·특정 부위라고 채우지 않는다. `고추장`과 `초고추장`, `생크림`과 `휘핑크림`처럼 성질이 다를 수 있는 품목을 유사 표기만으로 합치지 않는다.
- 붙어 있는 품목을 사전 최장 일치만으로 자르지 않는다. `국간장`은 `국`과 `간장`이 아니며 `진간장`·`국간장`은 별개다. `당근 노랑 파프리카`처럼 목록 문맥이 분명한 경우에만 각각 나눈다. 나눈 재료 중 어떤 것에 수량이 붙는지 불명확하면 수량을 복제하지 않는다.
- `돼지갈비양념` 같은 소스명, `치킨스톡` 같은 가공품에 육종명이 들어 있다는 이유로 고기 재료를 별도 생성하지 않는다. 메뉴 이름만으로 일반 레시피의 구성 재료를 추가하지 않는다.
- `대파/쪽파`가 대체 후보를 뜻하면 둘을 모두 사용한 것으로 기록하거나 한 재료의 전역 별칭으로 합치지 않는다. 둘 다 사용했다는 문맥이면 별개 재료로 기록하고, 실제 선택을 모르면 원문과 후보를 미확정정보에 남긴다.
- 전체 기간의 동일 표준명은 하나의 재료ID로 관리한다. 통합 전후의 원본 표기와 근거를 재료분류사전·행별재료수량에 보존한다. 같은 품목인지 불확실한 이름은 임의 병합하지 않으며, 후속 근거로 표준명이 바뀌면 별칭과 모든 참조 ID도 함께 갱신한다.

### 6.2 통계 계층

- L1: 현재 DB `통계분석군`.
- L2: 기본 식재료/종. 예: 돼지고기, 닭고기, 고등어, 오징어, 감자, 두부.
- L3: 부위·제품군. 예: 후지, 삼겹살, 가슴살, 연두부. 알 수 없으면 `미상`.
- L4: 표준재료명. 전처리·가공 형태 등 식별에 필요한 특징을 포함한다.

L1은 다음 값만 사용한다.

`곡류·주식 | 면·떡·전분 | 소고기 | 돼지고기 | 닭·오리 | 수산물 | 달걀 | 두류·두부 | 채소 | 버섯·해조 | 과일·견과 | 유제품 | 김치·절임 | 가공식품 | 장류·소스·조미료 | 기타`

예: 돼지고기다짐육은 `돼지고기 → 돼지고기 → 미상 → 돼지고기다짐육`, 돼지갈비양념은 `장류·소스·조미료`다. 돼지갈비양념이 있다고 돼지고기가 제공됐다고 집계하지 않는다.

김치·절임 완제품은 `김치·절임`, 소스는 `장류·소스·조미료`, 복합 가공품은 `가공식품`으로 분류한다. 단순 절단·냉동 원재료는 원재료군을 유지한다. 실제 성분이 없는 가공품에서 육종을 추정하지 않는다.

현재 DB는 L1 한 단계만 저장한다. L2~L4와 포장·가공 속성은 최종 보조 파일에 보존한다. 재료 사용 역할 `주재료/부재료/양념/미상`은 메뉴별로 기록한다. 기준정보의 `분석제외=N`, `사용여부=Y`를 기본으로 하고 임의로 재료를 통계에서 제거하지 않는다.

## 7. 수량·단위와 100인 환산

### 7.1 원본 수량의 의미를 먼저 확정

`재료 대상 → 실제 투입/준비 여부 → 원본 수량의 의미 → 원본 단위·규격 → 적용총량·적용단위 → 100인량` 순서로 처리한다. 단위부터 일괄 채우거나 모든 숫자를 총량으로 읽지 않는다.

- `원본수량의미`는 `총준비량/1인량/100인량/포장규격/입고량/재고량/추가주문량/미상`으로 구분한다. 조리 시간·온도·두께·크기·인원은 재료 수량이 아니다. `갈비 20kg, 200도 10분`에서 재료 수량은 20kg뿐이다.
- 수량을 가까운 명사에 무조건 붙이지 않는다. 문장의 대상·구분자·단위 범위를 확인한다. `양파·당근 각 2kg`은 각각 2kg, `양파·당근 합계 2kg`은 나누지 않는다. 여러 메뉴에 공동 사용한 총량도 배분 근거 없이 각 메뉴에 복제하거나 균등 배분하지 않는다.
- `3+3kg`, `500g×4봉`은 같은 재료의 별도 추가량/봉당 규격임이 명확할 때만 계산한다. 재고와 입고를 더하거나 이미 총량으로 적힌 값에 포장 수를 다시 곱하지 않는다. `2박스×10봉×500g`은 단계별 규격이 명시된 경우만 10kg으로 계산한다.
- 수량이 없거나 `적당량/조금/일부`면 미상이다. `2~3kg`, `약 3kg`, `반 정도`처럼 범위·근사 표현은 정확한 값으로 위장하지 말고 원문과 후보를 보존하며 확정 수량은 비운다. `반 봉`처럼 정확한 분수와 대상 단위가 분명하면 0.5봉으로 계산할 수 있다.
- 명시적인 숫자 0과 미입력은 구별한다. 음수·비정상 수치·서로 상충하는 수량은 임의로 절댓값/평균/최댓값으로 고치지 않는다. 이상값을 근거 없이 정상 범위로 바꾸지 말고 `검토필요`와 사유를 남긴다.
- 같은 재료가 반복되면 실제 추가 투입인지, 동일 내용 재서술인지 먼저 확인한다. 별도 추가량만 합산하며, 단위 환산이나 일부 추가량이 미상이라면 알려진 일부 합계를 전체 수량으로 출력하지 않는다. 원본 표현별 상세 기록은 각각 남기고 `근거`에 `사용량반영/실제추가/중복언급/비사용/미확정`을 구별해 적는다. 중복언급·비사용 상세 행은 원본 수량만 보존하고 적용총량·100인환산량은 비워 이중 합산을 막는다.

### 7.2 단위 표준화·포장 환산·준비 기준

업로드용 A파일의 단위는 다음 코드 또는 빈 값만 사용한다. 목록 밖 원문 단위는 B파일에 그대로 보존한다.

`kg | g | L | ml | 개 | 봉 | 팩 | 판 | 통 | 캔 | 병 | 박스 | 단 | 묶음 | 장 | 줄 | 포 | 관 | 밧트`

- `㎏/KG/키로/킬로/킬로그램→kg`, `그램/그람/그라→g`, `리터/ℓ→L`, `밀리리터/mL→ml`로 정리한다. `cc`가 부피 단위임이 명확하면 `1cc=1ml`로 환산한다. `봉지→봉`, `BOX→박스` 등 의미가 확실한 동의 표기는 통일하되 `봉/팩/포/통`을 무조건 같은 단위로 합치지 않는다.
- 누락 단위는 **같은 파일의 동일 품목·규격·사용 문맥에 단위가 명시된 근거**가 있고 상충 사례가 없을 때만 보완한다. 근거source_ref와 `문맥보완`을 기록한다. 숫자 크기·식재료 상식·다른 품목의 단위·마스터 기본단위만으로 kg을 추정하지 않는다.
- 중량과 부피는 별도 차원이다. 정확한 관계 `1kg=1000g`, `1L=1000ml`로 계산하고, 동일 재료의 비교 가능한 중량은 kg, 부피는 L로 적용량을 통일한다. 원본 단위와 원본 수량은 바꾸지 않는다. 단위를 바꾸면 적용 수량도 함께 환산한다.
- 포장 규격이 명시되어 있고 실제 사용한 포장 수가 확정되면 그 행에서만 중량·부피·개수로 환산한다. `12봉(1봉당400g)`은 4.8kg이다. `400g`이 봉당인지 총량인지 모르면 환산하지 않는다. 일부만 사용한 봉을 전량 사용한 것으로 계산하지 않는다.
- 서로 다른 포장 크기는 같은 재료ID에서도 행별로 계산한다. 어느 날 확인한 1봉=400g을 다른 규격·불명 규격의 봉에 적용하지 않는다. 총중량/순중량/고형량이 함께 있으면 실제 투입 대상이 무엇인지 확인하며, 알 수 없으면 임의 선택하지 않는다.
- 규격이 없으면 확인된 `봉/팩/판/개/장` 등을 그대로 유지한다. 달걀1판=30개, 관=특정 kg, 1개=특정 중량을 상식으로 적용하지 않는다. `T/t/티/스푼/국자/인분`도 원문에 의미·환산 근거가 없으면 임의의 ml·g·개로 바꾸지 않는다. 허용 코드로 표현할 수 없는 단위는 A파일의 해당 수량·단위를 비우고 B파일과 원본비고에 보존한다.
- L/ml와 kg/g은 서로 바꾸지 않는다. 명시된 품목별 밀도 등 환산 근거가 있을 때만 별도 계산하고 근거를 남긴다. 삶기 전/후 중량·손질 손실률·수율도 원문 근거 없이 환산하지 않는다.
- `03.기본단위`는 근거가 있는 적용단위들을 비교해 정한다. 모두 같은 차원으로 환산되면 kg 또는 L, 동일 개수/포장 단위만 확인되면 해당 코드를 사용한다. kg와 봉처럼 환산 불가능한 단위가 섞이면 기본단위를 비우고 단위선정근거에 사유를 남긴다. 이 값으로 과거 행의 누락 단위를 확정하지 않는다.
- `kg환산계수`는 원칙적으로 비운다. 꼭 필요하면 원문에 확인된 고정 규격과 적용 대상 단위가 전 기간 일치할 때만 사용한다. 재료당 하나인 계수를 혼합 포장·개수·부피 단위에 함께 적용하지 말고, 가능한 환산은 행별로 끝낸 뒤 적용단위 kg로 출력한다.

**중식 총 준비량은 400명 기준, 석식 총 준비량은 50명 기준으로 읽는다. 실식수는 환산 분모가 아니다.** 단위 정리 후 수량 의미별로 다음을 계산한다. N은 중식400 또는 석식50이다.

| 원본 수량의 의미 | 적용총량(`07.수량`) | 100인량(`05` 또는 상세 파일) |
|---|---|---|
| 총준비량 q | q | q × 100 / N |
| 1인량 q | q × N | q × 100 |
| 100인량 q | q × N / 100 | q |
| 포장규격만 있고 사용 수 없음 | 빈 값 | 빈 값 |
| 입고·재고·주문량만 있고 사용량 미확정 | 사용량으로 채택하지 않음 | 빈 값 |

- `07`의 계산 총량은 관측된 총량과 구별해 `규칙계산` 및 산식을 보존한다. 1인량·100인량을 그대로 `07.수량`에 넣으면 importer에서 다시 환산되므로 금지한다. 역산에 실제 식수를 쓰지 않는다.
- 계산에는 Decimal을 사용하고 중간 반올림을 하지 않는다. 확정된 적용단위를 인원 환산 과정에서 다시 바꾸지 않는다. 중식3봉은 100인량0.75봉이며, 소수 포장량을 올림하거나 소량 재료를 0으로 반올림하지 않는다.
- `70명 기준`처럼 원문이 다른 준비 기준을 직접 명시하면 `기준인원상충`으로 기록한다. 해당 행의 확정 적용총량/100인량은 비워 두고 원본 총량, 준비인원, 기본기준·원문기준 환산 후보를 B파일에 보존한다. 후보도 원본 수량 의미를 먼저 구별해 계산하며, 메뉴 하나의 예외로 날짜×배식 전체 계획식수를 바꾸지 않는다.
- 수량상태·단위상태는 적용값을 확정한 근거에 따라 `원문명시/규칙계산/문맥보완/미상`으로 기록한다. 수량 숫자가 명시되어도 단위가 미상이면 각각 다른 상태를 기록할 수 있다. 후보값을 확정 적용값에 넣지 않는다.

| 원문과 문맥 | 적용총량·적용단위 | 100인량 | 주의점 |
|---|---|---|---|
| 중식 양파20kg | 20kg | 5kg | 중식 ÷4 |
| 석식 소스1500ml | 1.5L | 3L | 부피 정리 후 석식 ×2 |
| 중식 쌀국수12봉, 봉당400g 전량 사용 | 4.8kg | 1.2kg | 12×400÷1000, 포장·중량 이중 집계 금지 |
| 중식 만두1인3개 | 1200개 | 300개 | 07에 3개를 넣지 않음 |
| 석식 소스100인당200g | 0.1kg | 0.2kg | 07에 100인량을 그대로 넣지 않음 |
| 중식 만두3봉, 봉당 규격 미상 | 3봉 | 0.75봉 | kg으로 추정하지 않음 |
| `마늘 2`이며 단위 근거 없음 | 빈 값 | 빈 값 | 원문 숫자2는 B파일에 보존 |

### 7.3 결과에 저장할 값

- `01_배식설정.기본계획식수`와 `06_식단이력_이관.계획식수`: 중식400, 석식50. 다른 운영 기본값으로 대체하지 않는다.
- `07_식단재료_이관.수량`: 확정한 적용총량. 원문이 총량이면 단위 정리 후 총량, 1인량/100인량이면 위 식으로 계산한 준비 총량을 넣는다. 단위는 해당 적용총량과 한 쌍으로 기록한다.
- `05_메뉴별재료_기준.100인기준수량`: 8.3에서 선택한 대표 사례의 확정 100인량만 넣는다. 다른 날의 `07` 수량을 이 값에 맞춰 바꾸지 않는다.
- 단위 미상·지원하지 않는 단위·수량 대상 불명·기준인원 상충은 `05/07`의 확정 수량을 비운다. 사용 재료라는 사실이 확정됐다면 재료 행 자체는 유지하고, 원본 수량·단위·미상 사유는 B파일 및 원본비고에 남긴다.
- importer는 `05/07`의 빈 단위를 `03.기본단위`로 대체할 수 있다. 따라서 단위 미상 숫자를 넣은 채 단위만 비워 두지 않는다. DB에 표시된 기본단위를 원문의 확정 단위라고 주장하지 않는다.
- 같은 식단메뉴·같은 재료의 확정량은 정확히 환산 가능한 단위끼리만 합쳐 `07` 한 행으로 만든다. 단위 혼합이나 일부 추가량 미상으로 총량을 확정할 수 없으면 그 행의 수량은 비우고 상세 파일에 각각의 원문값을 보존한다. `05`의 같은 블록에서도 재료ID 중복 행을 만들지 않는다.
- 배식시간은 원문에 없으면 빈 값이다. importer가 운영 기본시간을 적용할 수 있으므로 원문에서 확인한 시간과 구별한다. 시간을 묻기 위해 작업을 멈추지 않는다.

## 8. 레시피: 의미 있는 구성 차이만 유형으로 구분

### 8.1 레시피를 적당한 수로 묶는 기준

**같은 메뉴ID에서 실제 요리의 정체성을 이루는 재료 구성이 같으면 하나의 레시피 유형으로 묶는다.** 정규화한 재료ID 집합이 정확히 같으면 반드시 같은 유형이다. 집합이 달라도 아래의 비핵심 차이만 확인된다면 새 레시피를 만들지 않는다. 수량·비율·단위·포장 규격·날짜·배식유형·조리 시간만 다른 경우도 나누지 않는다. 레시피 수를 줄이려고 서로 다른 메뉴ID를 병합하거나 중요한 주재료 변경을 숨기지 않는다.

각 제공일의 **실제 기재 재료 전체 집합**과 레시피를 묶는 **핵심 구성(유형키)**을 따로 만든다. 유형키는 동일 메뉴ID 내에서 확인된 ① 요리 형태/주식·주단백질·주요 채소 등 중심 재료, ② 메뉴 특징을 결정하는 속재료·곁들임, ③ 음식의 정체성을 바꾸는 주요 소스/양념의 표준재료ID를 정렬한 목록이다. 같은 실제 음식인데 표기만 다른 재료는 먼저 표준화하고, 동일한 핵심 재료의 양 차이는 유형키에 넣지 않는다.

- **분리:** 주식/주단백질의 추가·제거·대체, 요리의 주된 채소/과일·속재료·주요 소스가 실제로 바뀌어 다른 음식으로 설명할 수 있는 경우. `샐러드`의 마카로니형과 과일형, `잡채`의 돼지고기형과 해물형, `감자조림`의 간장형과 고추장형은 구분한다. 제공이 단 한 번이어도 명백히 다른 주재료면 별도 유형이다.
- **통합:** 양파·대파·마늘·소금 같은 통상적인 공통 부재료/향신료의 기재 유무, 부재료 소량 증감, 이름·형태가 동일한 식재료의 표기/규격 차이, 특징을 바꾸지 않는 장식·고명 차이만으로는 새 유형을 만들지 않는다. 단, 부재료라도 메뉴명에 명시되거나 그 음식의 특징/제공 방식을 바꾸면 핵심으로 취급한다.
- **문맥 판단:** 모든 양념을 무조건 비핵심으로 내리거나 모든 추가 재료를 새 레시피로 취급하지 않는다. `담양식 국수`에서 맛김치·계란지단과 소고기·애호박이 서로 다른 실제 구성으로 확인되면 구분한다. 이름만 달라졌거나 부재료 기재가 빠진 것만으로 그런 차이를 만들어 내지 않는다.

같은 메뉴ID에서 먼저 정확히 일치하는 전체 재료 집합을 합치고, 그다음 핵심 구성과 문맥이 같은 집합끼리 유형으로 묶는다. `샐러드`처럼 범용 메뉴명에 여러 실제 요리가 들어갈 수 있으면 이름만 보고 하나로 합치지 않고 위의 핵심 재료로 나눈다. 각 제공일의 정확한 재료 집합·수량·출처는 `07_식단재료_이관`과 상세 파일에 그대로 남긴다. 유형의 재료를 과거 제공일에 실제로 사용한 것처럼 추가하지 않는다. 모든 메뉴에 일률적으로 1개 또는 일정 개수만 강제하지 않는다.

통계집계명이 같아도 실제 메뉴ID가 다르면 DB의 레시피도 따로 유지한다. `/` 앞 메뉴만으로 통계집계명을 정했더라도 메뉴명 전체와 해당 메뉴의 실제 재료 이력을 삭제하거나 다른 메뉴ID의 레시피와 합치지 않는다.

### 8.2 일부만 기재된 행과 신규 유형 판정

원문에 재료가 덜 적힌 것과 실제로 빠진 것은 다르다.

- `나머지 동일`, `양만 조절`, `전과 동일`처럼 명시적 이어쓰기 관계가 있고 참조 메뉴/날짜가 하나로 결정되면 확인되는 유형에 연결한다. 빠진 재료·수량은 그날의 이력에 복사하지 않는다.
- 기재된 핵심 재료만으로 기존 유형 **하나**가 분명하면 `유형만연결`로 연결하되, 기재되지 않은 비핵심 재료를 해당 일자의 사용 재료로 채우지 않는다. 둘 이상 가능하거나 핵심 변경 여부가 불분명하면 `구성미상`으로 남기고 확정 레시피 연결을 비운다.
- 새 행이 기존 전체 재료 집합의 일부라는 이유만으로 빠진 재료를 자동 추가하지 않는다. 내용이 비었거나 메모뿐인 행은 빈 구성의 신규 레시피로 만들지 않는다.
- 신규 유형은 **확인된 핵심 재료/요리 형태의 실질적인 차이가 있고 그 차이를 원본 행으로 지목할 수 있을 때만** 만든다. 단순히 1회만 등장했거나 기록이 짧다는 이유로 유형을 추가하지 않는다. 사례 횟수가 적다는 이유만으로 명확히 다른 주재료를 병합하지도 않는다.
- 전체 처리 후 같은 메뉴의 유형들을 다시 비교해 핵심 차이가 없는 중복을 합치고, 실제로 다른 핵심 구성이 합쳐지지 않았는지 내부적으로 확인한다. 별도 중간 검증·승인 단계는 만들지 않는다.

### 8.3 유형당 대표 사례와 기준 수량 선택

한 유형에서 날짜별 수량과 비핵심 재료가 달라도 마스터 레시피는 **실제 기록된 대표 사례 하나의 전체 재료 구성**으로 만든다. 서로 다른 날짜의 재료를 합쳐 가상의 레시피를 만들지 않는다. 그날의 실제 재료·총량은 식단재료 이력에 각각 보존한다.

1. 해당 유형 내에서 **동일한 전체 재료 집합이 가장 자주 관찰된 사례**를 우선한다.
2. 동률이면 기준인원 상충이 없고 100인량·단위를 확정할 수 있는 재료가 많은 사례를 고른다.
3. 다시 동률이면 가장 최근 날짜, 다시 동률이면 가장 작은 원본 행번호를 고른다.

선택 사례의 확정 100인량만 `05_메뉴별재료_기준`에 넣는다. 수량 미상은 빈 값으로 두고, 다른 날의 수량을 섞어 채우지 않는다. 유형키와 대표 사례의 전체 재료 집합은 서로 다른 개념이며, 후자는 현재 이관기에 저장되는 실제 마스터 레시피 재료 목록이다.

## 9. 레시피명: 메뉴명 + 구성을 구별하는 재료 특징

레시피명 형식은 **`메뉴명 - 특징재료형`**으로 통일한다.

1. 같은 메뉴의 **서로 다른 레시피 유형** 사이에서 실제로 차이를 만드는 핵심 재료를 우선 찾는다. 비핵심 재료의 기재 차이로 합친 유형에는 이름을 여러 개 만들지 않는다.
2. 주재료·주요 소스·특징 부재료 중 최대3개를 선택한다. 동일 조건에서는 `주재료 → 소스 → 부재료 → 양념` 순, 같은 역할에서는 표준재료명 사전순으로 고른다.
3. 양파·대파·소금처럼 유형 구분과 무관한 재료보다는 실제 차이를 만드는 재료를 우선한다.
4. 유형이 하나뿐이어도 그 유형의 대표 사례에 실제 기재된 주요 재료를 사용해 이름을 만든다. `기본 레시피 v1` 같은 번호 중심 이름을 생성하지 않는다.
5. 같은 유형은 날짜·수량·비핵심 재료 기록이 달라도 같은 보조 레시피ID와 같은 이름을 사용한다.
6. 이름에 수량·인원·날짜를 넣지 않는다. 원문에 없는 재료나 `매운맛` 같은 확인되지 않은 맛을 넣지 않는다.
7. 다른 유형인데 같은 이름이 되면 추가 특징재료로 구별한다. 그래도 같으면 유형키 해시 앞8자리를 접미사로 붙인다.
8. DB 길이 제한을 고려해 레시피명은 120자 이내로 만들고, 긴 이름은 특징 부분을 줄인다. 전체 원본 메뉴명과 재료 구성은 별도 열에 보존한다.
9. 레시피명은 파일 간 레시피 연결키로도 쓰인다. 같은 메뉴ID 안에서 레시피명과 유형(05 블록)은 1:1이어야 하며, 서로 다른 유형에 같은 이름을 쓰거나 한 유형에 두 이름을 쓰지 않는다. 최종 확정한 이름은 `05.레시피명`, `06.레시피명`, B파일 `레시피목록.레시피명`, `식단레시피연결.레시피명`에 글자·띄어쓰기·기호까지 동일하게(NFC) 기록하고, 통합 후 이름을 바꾸면 모든 위치를 함께 갱신한다.

예시의 재료가 실제 구성에 있을 때만 다음과 같이 이름을 붙인다.

| 메뉴명 | 실제 재료 구성의 특징 | 레시피명 예시 |
|---|---|---|
| 담양식국수 | 맛김치·계란지단 | 담양식국수 - 맛김치·계란지단형 |
| 담양식국수 | 소고기·애호박 | 담양식국수 - 소고기·애호박형 |
| 잡채 | 돼지고기·부추 | 잡채 - 돼지고기·부추형 |
| 잡채 | 돼지고기·표고버섯 | 잡채 - 돼지고기·표고버섯형 |
| 감자조림 | 간장 | 감자조림 - 간장형 |
| 감자조림 | 고추장 | 감자조림 - 고추장형 |

레시피 이름은 최종 통합 시 다른 유형과의 핵심 차이를 반영해 완성한다. 최초 임시 이름 때문에 동일 유형이 여러 레시피로 남지 않게 한다.

## 10. 실식수와 식단 연결

- 실식수는 D열에서만 읽는다. 날짜×배식유형당 한 번만 기록한다.
- 동일 배식의 여러 메뉴 행에 같은 실식수가 반복되어도 합산하지 않는다.
- 빈 값과 같은 숫자가 섞이면 그 숫자를 한 번 채택한다. 모두 비어 있으면 미입력, 명시0이면 실제0이다.
- 서로 다른 실식수가 있으면 해당 배식의 확정값은 비우고 원문값들을 최종 특이사항에 남긴다. 최댓값·평균값을 임의 선택하지 않는다.
- 메뉴명이나 조리 메모의 `70명기준`, `300명 밖에 못 먹음`은 준비량/운영 메모일 수 있으므로 실식수로 옮기지 않는다.
- 향후 재료와 실식수를 연결할 수 있도록 날짜·배식유형·메뉴ID·재료ID를 유지한다. 같은 배식에 같은 재료가 여러 번 등장해도 제공 여부 집계는 한 번이어야 한다.
- 실식수와 재료 제공의 관계를 곧바로 개인의 선호나 인과효과라고 단정하지 않는다. 여기서는 분석용 데이터를 만들고 선호 순위를 생성하지 않는다.

### 메인 메뉴 판정

메인 메뉴는 메뉴 마스터의 고정 속성이 아니라 **날짜×배식유형별 식단 메뉴의 속성**이다. 중식과 석식을 합쳐 하루에 한 개로 고르지 않는다. 같은 메뉴도 어느 식단에서는 메인이고 다른 식단에서는 아닐 수 있다.

1. 그 식단의 실제 메뉴와 이어쓰기 행의 귀속을 모두 확정하고, 메모·취소 메뉴를 제외한 원본 등장 순서로 메뉴순서를 부여한다. 메뉴명·역할을 최종 정규화한 뒤 메인을 판정한다.
2. `/`로 조합된 메뉴는 4.5의 첫 `주요리명`만 후보 판정에 사용한다. 수식어·괄호의 지시보다 실제 요리의 성격을 본다. 뒤의 곁들임에 볶음밥이 있다고 첫 메뉴를 일품밥류로 취급하지 않는다.
3. 비빔밥·볶음밥·덮밥·카레라이스처럼 밥과 재료가 하나의 완성 요리를 이루는 **일품밥류를 최우선 후보**로 정한다. 쌀밥·잡곡밥·흑미밥처럼 일반 반찬과 함께 먹는 기본 밥은 이 예외가 아니다. `밥`이라는 글자만으로 일품밥류라고 판단하지 않는다.
4. 일품밥류가 있으면 그중 메뉴순서가 가장 빠른 하나를 `Y`로 한다. 주찬이 더 앞에 있어도 일품밥류가 우선이다. 일품밥류가 없으면 역할이 `주찬`인 메뉴 중 메뉴순서가 가장 빠른 하나를 `Y`로 한다.
5. 나머지 메뉴는 모두 `N`으로 한다. 후보가 없거나 후보 여부를 확정할 수 없으면 임의로 국·김치·면 등을 메인으로 승격하지 않고 모두 `N`으로 두며 사유를 남긴다. 후보가 확정된 식단은 `Y`가 정확히 한 건, 그 외는 0건이어야 한다.
6. 재료량·가격·고기 함량·레시피 존재 여부로 우선순위를 바꾸지 않는다. 메인인 볶음밥도 역할은 `밥·죽`으로 유지한다. 정규화나 역할 변경이 있으면 해당 식단 전체의 메인 표시를 다시 계산한다.

`식단레시피연결.메인메뉴판정근거`에는 주요리명과 `일품밥우선/첫주찬/후순위/후보없음/판정미확정` 사유, 필요한 source_ref를 짧게 기록한다. 이 근거는 B파일에 보존하고 실제 조리법·특이사항과 섞지 않는다.

| 원본 메뉴순서대로 나열한 한 식단 | 메인 메뉴 | 판단 |
|---|---|---|
| 잡곡밥 → 미역국 → 탕수육 → 제육볶음 | 탕수육 | 일반 밥은 제외, 첫 주찬 |
| 탕수육 → 김치볶음밥 → 배추김치 | 김치볶음밥 | 순서와 무관하게 일품밥 우선 |
| 비빔밥 → 볶음밥 → 돈까스 | 비빔밥 | 일품밥 후보 중 첫 메뉴 |
| 생선까스/볶음밥 → 소고기국 → 김치 | 생선까스/볶음밥 | 주요리명은 생선까스, 일품밥 예외가 아니라 첫 주찬으로 선정 |
| 쌀밥 → 콩나물국 → 배추김치 | 없음 | 후보가 없으므로 전부 N |

위 예시는 판단 규칙 확인용이며, 실제 원문에 없는 식단·메뉴·재료를 생성하지 않는다.

## 11. ID·정렬과 일관성

- 표준 메뉴명/표준재료명은 Unicode NFC로 정규화하고, 한글 복합명사는 의미가 보존되는 범위에서 띄어쓰기 없이 표기한다. 고유명·외래어 등 공백이 필요한 경우에만 유지한다. 원본 표기는 별도 원문 열에 그대로 보존한다. 메뉴ID와 재료ID는 이 최종 정규화 이름으로 계산해 띄어쓰기만 다른 중복 ID가 생기지 않게 한다.
- 메뉴ID: `M_` + 정규화 메뉴명 UTF-8의 SHA-256 앞24자리.
- 재료ID: `I_` + 표준재료명 UTF-8의 SHA-256 앞24자리.
- 보조 레시피ID: `R_` + `[메뉴ID, 정렬한 핵심 구성 표준재료ID 목록]`의 JSON UTF-8 SHA-256 앞24자리. JSON은 ensure_ascii=false, 공백 없는 separators를 사용한다. 동일 유형의 비핵심 재료 차이나 대표 사례 변경으로 ID를 다시 만들지 않는다.
- 수량·단위·레시피명은 레시피ID 계산에 넣지 않는다. 핵심 재료를 확정할 수 없어 둘 이상의 유형이 가능하면 보조 레시피ID를 임의로 배정하지 않는다. 이 ID는 보조 파일의 유형 연결키이며 DB PK나 DB 내부 composition_key가 아니다.
- 같은 대상은 파일 전체에서 같은 ID를 사용한다. ID는 프로그램으로 계산한다. 해시 충돌 시 임의로 병합하지 말고 해당 항목을 미확정 정보로 남긴 채 다른 행은 계속 처리한다.
- 식단 메뉴순서는 날짜×배식별 원본의 실제 메뉴 등장 순서대로 1부터 부여한다. 메모행은 메뉴순서를 증가시키지 않는다.
- 재료순서는 각 레시피 또는 식단메뉴별로 1부터 부여한다. 같은 재료의 반복 언급은 하나로 묶고, 같은 의미·단위의 명시 추가량만 합산한다.
- 불명확한 값을 마스터 기본값으로 숨기지 않는다. `검토상태`는 필요한 스키마 필드일 뿐이며 `정상/검토필요`로 표시하고 승인 요청은 하지 않는다.

`05`의 출력 규칙:

- **메뉴×확정된 핵심 구성 유형마다 한 블록**만 출력한다. 비핵심 재료·수량 차이만 있는 날짜별 변형을 별도 블록으로 내보내지 않는다.
- 한 블록에는 8.3에서 고른 **실제 대표 사례의 전체 재료 집합**만 기록한다. 비핵심 재료를 모든 제공일에 사용한 것으로 만들어 기록하거나, 여러 날의 재료를 합쳐 대표 사례를 조작하지 않는다.
- 블록 안에서는 같은 레시피명을 반복하고 재료순서를 1부터 증가시킨다. 다음 유형 블록에서 재료순서를 다시1로 시작한다.
- 메뉴ID별로 블록을 연속 배치한다. 같은 메뉴 안에서는 유형 출현 횟수 내림차순, 동률이면 유형키 사전순으로 블록을 배치한다. 첫 유형이 기본 레시피 후보가 된다.
- 같은 블록의 재료ID는 중복되지 않아야 하며, 선택한 사례의 100인량을 사용한다.
- 구성미상 행은 새 유형 블록으로 만들지 않는다. 식단 이력과 확인된 재료 이력은 가능한 범위에서 보존한다.

`06.레시피명`에는 그날 제공한 레시피 유형의 이름을 적는다. 값은 **같은 메뉴ID의 `05.레시피명` 중 하나와 정확히 일치**해야 하며, 다른 메뉴ID의 레시피명을 쓰지 않는다. 연결상태가 `정확구성` 또는 `유형만연결`이면 해당 유형의 레시피명을 쓰고, `구성미상`이거나 재료가 기재되지 않아 유형을 정할 수 없으면 추측하지 말고 빈 값으로 둔다.

`07`에는 그날 실제로 확인한 재료만 기록한다. `정확구성`이면 그날의 `07` 재료ID 집합이 `06.레시피명` 블록(`05`)의 재료ID 집합과 같아야 한다. 비핵심 재료의 기재 차이가 있는 `유형만연결`은 `07`을 레시피 구성에 맞춰 고치지 않고 실제 재료를 그대로 둔다. 그 차이는 B파일 `식단레시피연결`의 `연결상태`·`사유`·`실제재료ID목록`에 기록한다.

`06.메인메뉴여부`와 `식단레시피연결.메인메뉴여부`는 메인 메뉴이면 `Y`, 아니면 `N`으로 기록하고 날짜×배식유형×메뉴순서×메뉴ID 기준으로 같은 값을 사용한다. `06.메뉴비고`에는 `[조리법]`, `[배식]`, `[특이사항]`으로 분리한 내용을 넣는다. `07.원본비고`에는 단위 보완·수량 의미·미상 사유, `원본행`에는 source_ref를 넣는다. 날짜×배식×메뉴순서×메뉴ID는 `06/07`에서 동일하게 사용한다.

### A·B·C 공통 최종 내부 검증

전 행 처리와 사전 통합 후 다음을 내부 검증한다. 형식·참조·허용 코드·수량 계산·판정 결과의 일관성은 프로그램으로 검사하고, 명칭·역할·부정/대체 지시·메모 귀속의 의미는 AI가 원문과 대조해 재검토한다. 파일을 실제로 저장한 뒤 다시 열어 시트명·헤더·행 수·ID 참조·수량·메인 표시가 보존됐는지도 확인한다. 형식·참조·계산 오류는 근거에 맞게 고친다. 의미를 확정할 수 없는 항목은 빈 값과 사유로 남기며, 검증을 통과시키려고 값을 지어내지 않는다. 중간 보고서나 승인 대기 절차로 전환하지 않는다.

**원문 추적·형식·명칭**

- 원본 데이터 행의 source_ref 집합과 `행별정제결과`의 source_ref 집합이 같고 원문 6개 열이 보존된다. 원본 행이 메뉴·재료·독립메모·미확정 중 어디에 반영됐는지 추적 가능하며 누락·출처 없는 생성 행이 없다.
- A파일은 정해진 7개 시트/헤더, B파일은 정해진 8개 시트/헤더, C파일은 실제식수정보 시트를 갖는다. 숫자 입력 칸에 `미상/-/약/범위` 같은 텍스트나 수식을 넣지 않는다. 원문·계산식 필드의 `=`, `+`, `-`, `@`로 시작하는 내용도 실행 가능한 수식이 아니라 텍스트 셀로 저장한다.
- 모든 메뉴ID·재료ID가 해당 기준정보에 존재하며 ID와 표준명의 관계가 파일 전체에서 일치한다. 별칭은 하나의 재료ID에만 연결된다. 이름에 조리 지시·수량·인원·재고 메모가 남았거나 의미가 다른 품목을 합친 경우 원문 근거로 다시 검토한다.
- 메뉴역할·통계분석군·단위는 허용 코드 범위에 있고, 같은 메뉴ID의 역할이 일관된다. `/` 조합 메뉴의 집계명·역할·메인 후보가 모두 첫 주요리명 기준인지 확인한다. `탕수육→국·탕`, `국수→국·탕` 같은 부분 문자열 오분류를 재검토한다.

**수량·단위·환산**

- 확정 수량마다 대상 재료·수량 의미·적용단위·준비 기준·근거가 있으며, 적용값은 음수가 아닌 유한 숫자다. 원문 숫자가 있다는 이유만으로 단위 미상·근사량·공동 총량·입고량을 확정 사용량으로 출력하지 않는다.
- 날짜×배식유형×메뉴순서×재료ID별로 상세 파일의 `사용량반영/실제추가` 값만 합친 최종량과 `07`을 대조한다. 중복언급·비사용은 합산하지 않고, 실제 추가량 중 미확정이 있으면 최종 총량도 미확정으로 둔다. 확정된 `07.수량 × 100 / 06.계획식수`는 이렇게 집계한 상세 100인환산량과 단위까지 일치해야 한다. `05` 수량은 선택한 대표 사례의 최종 100인량과 일치하며, 다른 날짜의 사용량을 마스터 값과 같게 강제하지 않는다.
- 중식/석식, 총량/1인량/100인량, kg/g, L/ml, 포장 규격 환산을 각각 점검한다. 7.2 예시의 4.8kg→중식100인량1.2kg, 1인3개→중식총량1200개, 석식100인당200g→총량0.1kg 등이 그대로 계산되는지 확인한다.
- 같은 메뉴·재료의 반복 표현을 이중 집계하지 않았고, 추가량 일부가 미상인 행의 알려진 부분합을 전체로 쓰지 않았다. 단위가 섞인 품목에 하나의 kg환산계수를 잘못 적용하지 않았다.

**식단·메인 메뉴·레시피 연결**

- `06`은 날짜×배식유형×메뉴순서가 식단 메뉴 한 건을 식별하고, `07`의 식단메뉴 키는 모두 `06`에 존재한다. 메뉴순서는 실제 메뉴 등장 순서를 보존하며 메모 때문에 증가하지 않는다. 이어쓰기 원본 행들은 B파일에서 출처를 모두 보존한다.
- `06.메인메뉴여부`는 모든 행이 `Y` 또는 `N`이다. 날짜×배식유형별 후보가 확정되면 일품밥 우선/첫 주찬 규칙으로 정확히 한 건이 `Y`, 후보가 없거나 미확정이면 모두 `N`이며 사유가 있다. B파일의 표시·판정근거와도 일치한다.
- 비어 있지 않은 모든 `06.레시피명`이 같은 메뉴ID의 `05.레시피명`으로 존재한다. 같은 메뉴ID의 `05`에서 이름과 블록은 1:1이며, 이름이 다른데 전체 재료ID 집합이 같은 중복 블록은 없다. 현재 importer는 이런 이름·구성 충돌을 오류로 거부한다.
- `정확구성`인 식단 메뉴는 `07` 재료ID 집합이 해당 `05` 블록과 같다. `유형만연결`은 이름으로 유형에 연결하되 그날 실제 재료와 차이 사유를 보존하고 `정확구성`으로 위장하지 않는다.
- 같은 식단메뉴에 대해 `06.레시피명`과 B파일 `식단레시피연결.레시피명`이 같고, 보조 레시피ID/이름 쌍은 `레시피목록`과 일치한다. 이름이 미확정인 행은 `06.레시피명`도 빈 값이다.

**조리법·특이사항·실식수**

- 조리법의 시간·온도·순서·대상, 배식 수량, 부정·조건·대체 지시가 원문에서 누락되거나 반대로 바뀌지 않았다. 재고·다음 주문·과거 평가를 현재 투입 재료나 조리 명령으로 바꾸지 않았다.
- 미귀속·배식 공통 메모는 독립메모에 남고, 메뉴별 메모는 올바른 날짜·배식·메뉴의 `06.메뉴비고`에 연결된다. 임의의 표준 조리법을 보충한 문장이 없다.
- C파일의 실제 식수는 날짜×배식당 하나이며 반복 메뉴 행을 합산하지 않았다. 원문의 명시0과 빈 값이 구별되고, 준비인원·기본계획식수를 실제 식수로 채우지 않았다.

`유형키`는 레시피ID를 만든 핵심 재료ID 목록, `대표구성키`와 `대표재료ID목록`은 05에 실제 출력한 한 사례의 전체 재료ID 목록이다. `식단레시피연결.실제재료ID목록`에는 그 제공일에 원문으로 확인한 재료 전체를 적는다. `연결상태`는 전체 재료가 대표구성과 동일하면 `정확구성`, 핵심은 같지만 비핵심 재료의 기재가 다르면 `유형만연결`, 판단 불가면 `구성미상`으로 구분한다. `06.레시피명`을 채우면 importer가 그 이름의 레시피에 연결하지만, `유형만연결`인 날의 실제 재료가 마스터 구성과 같아지는 것은 아니다. 이름이 빈 행만 13절의 구성 일치/기본 레시피 연결 제약을 적용받는다.

- `행별정제결과`는 원본 데이터 행마다 한 행을 남긴다. 한 원본 행이 여러 재료·메모로 분리돼도 원문 6개 열과 source_ref를 그대로 보존하고, 상세 재료·메모는 해당 source_ref로 연결한다. 메뉴·재료가 아닌 행도 삭제하지 않는다.
- `식단레시피연결`은 `06`의 식단메뉴별 한 행으로 기록하고 source_ref에는 그 메뉴가 시작된 원본 행을 적는다. 추가 이어쓰기 행은 `행별정제결과.귀속근거`로 기본 메뉴행과 연결하며, `행별재료수량`에는 확정된 일자·배식유형·메뉴순서를 함께 적는다. 이 키로 같은 날 같은 메뉴가 여러 번 나와도 수량을 다른 제공 건에 합치지 않는다. 귀속이 미확정인 키는 비워 둔다.
- `귀속근거`에는 명시된 메뉴/배식 대상, 병합 셀 범위, 이어쓰기 참조 source_ref 등 확인한 근거를 적는다. 원본 날짜·배식 열에는 상속한 값을 원문처럼 써넣지 않는다.
- `명칭정규화근거`·`역할판정근거`·`단위선정근거`·`메인메뉴판정근거`는 짧은 원문 근거와 적용 규칙을 남기는 열이다. 동일 표준명에 여러 원문 표기가 연결되면 대응 관계와 근거 source_ref를 추적할 수 있게 기록한다.
- 행별재료수량의 `원본수량`은 `3+3`, `2~3`, `약 3` 같은 원문 표현도 텍스트로 보존한다. `환산식`에는 수치·단위·포장 환산·준비인원까지 적는다. `포장규격`은 행별 규격이며, 사전의 여러 포장 규격을 모든 행에 공통 적용하지 않는다. `근거source_ref`에는 누락 단위 보완 등에 실제 참조한 행을 남긴다.
- 확정 수량·미상 후보를 섞지 않는다. 역할을 모르면 재료역할 `미상`, 분류 계층 L2~L4를 모르면 `미상`, 숫자·단위 등 확정 입력값을 모르면 빈 값으로 둔다. `검토필요`의 구체 사유는 `미확정정보`·`사유`·`근거`에 기록한다.
- 보조 열은 추적·검토용이며, 이를 업로드용 A파일의 임의 추가 열로 옮겨 DB에 저장된다고 주장하지 않는다. A파일의 7개 시트와 헤더는 그대로 유지한다.

없는 값은 빈 값으로 남긴다. 원본 수량과 총량·100인량을 분리하여 이력을 보존한다. 독립메모·구성미상·단위미상을 숨기지 않되 이를 해결하기 위해 중간 승인을 요구하지 않는다.

### C. 실제식수정보_업로드용.xlsx

- 시트는 `실제식수정보` 한 개만 만든다.
- 헤더: `일자 | 중식 | 석식 | 특이사항`.
- 날짜당 한 행, 중식/석식은 확정된 실식수 또는 빈 값이다. 반복 메뉴행을 합산하지 않는다.
- 식수 상충 등은 특이사항에 기록한다. 원문의 준비인원은 여기에 넣지 않는다.

## 13. 현재 DB·이관기의 지원 범위와 저장 제약

다음은 출력 파일을 올바르게 구성하기 위한 조건이며 별도 확인·승인 단계가 아니다.

- `Menu.name`은 실제 메뉴명, `Menu.canonical_name`은 수식어를 제거한 통계집계명이다. 동일 집계명에 여러 실제 메뉴가 연결될 수 있다. `Menu.role`은 메뉴별 속성이고 메인 메뉴 표시는 날짜×배식의 식단 메뉴별 속성이다.
- `Ingredient.stat_group`은 L1 하나만 저장한다. L2~L4·규격별 이력·판정 근거는 B파일에 보존한다.
- importer는 `05`에서 재료순서가 다시 시작하거나 레시피명이 바뀌면 블록을 구분하고, **각 블록의 전체 재료ID 집합**으로 DB 레시피를 식별한다. 유형당 대표 사례 블록 하나만 출력한다. 메뉴ID가 다르면 대표 구성이나 통계집계명이 같아도 별도 레시피다.
- **`05.레시피명`은 현재 DB 레시피 이름으로 저장된다.** 비어 있는 블록만 `기본 레시피 vN`으로 자동 명명한다. 같은 메뉴ID에서 동일 레시피명이 서로 다른 구성에 쓰이거나, 다른 이름들이 동일 구성을 가리키면 업로드 오류이므로 출력 전에 1:1 관계를 검증한다.
- **`06.레시피명`이 있으면 같은 메뉴ID의 해당 `05` 레시피에 명시적으로 연결한다.** 그 이름이 `05`에 없으면 업로드 오류다. `유형만연결`도 확정한 유형의 이름으로 연결할 수 있으며, 그날 실제 재료인 `07`의 구성·수량을 마스터 레시피와 같게 조작하지 않는다.
- `06.레시피명`이 빈 행은 `07`의 재료ID 집합과 정확히 일치하는 레시피, 없으면 해당 메뉴의 기본 레시피로 연결될 수 있다. `구성미상`이라고 해서 DB 레시피 연결도 반드시 비어 있는 것은 아니다. 이름 없이 연결된 이력의 한계는 최종 요약에 명시하고, 이를 감추려고 모르는 유형명이나 재료를 채워 넣지 않는다.
- 보조 레시피ID/유형키는 외부 연결용이다. DB 내부 composition_key는 대표 사례 전체 재료의 DB PK 집합이므로 외부 해시·핵심 재료ID 목록을 DB PK 또는 DB composition_key로 취급하지 않는다.
- `Recipe.note`, `is_primary`, 다단계 분류, 배식 전체 메모는 임의의 추가 열로 자동 저장되지 않는다. 조리법은 `06.메뉴비고`에, 독립메모와 기타 속성은 B파일에 보존한다. 재료의 주재료 여부와 식단의 메인 메뉴 여부를 혼동하지 않는다.
- 확정한 적용총량을 `07`에, 대표 사례의 100인량을 `05`에 넣어 이중 환산을 피한다. importer는 `07.수량 × 100 / 06.계획식수`를 계산하며 빈 단위를 기본단위로 대체할 수 있다. 단위 미상·기준인원 상충·부분 수량은 확정 입력값으로 넣지 않고 B파일에 보존한다.
- 업로드 시트와 상세 파일에 `메인메뉴여부`를 별도로 기록한다. importer는 `06.메인메뉴여부`의 `Y`/`N`을 `MealServiceMenu.is_representative`에 저장한다. 빈 값/허용값 이외의 값 또는 한 식단의 복수 `Y`는 오류이며, 전부 `N`인 식단은 허용된다. 열을 아예 생략하면 구형 파일의 첫 주찬 자동 지정으로 돌아가므로 이 작업에서는 열을 생략하지 않는다. 메인 지정에 맞추려고 메뉴역할을 거짓 `주찬`으로 바꾸지 않는다.

## 14. 최종 응답

자료를 행 단위로 끝까지 처리하고 **다음 내용만 최종 응답으로 제공하라.**

1. 실제 생성한 A·B·C 파일의 다운로드 링크.
2. 실제 처리한 원본 행 수, 메뉴 수, 재료 수, 핵심 구성 유형별 레시피 수, 날짜×배식 기준 식단 수, 실식수 배식 수. 같은 메뉴의 여러 유형·1회 등장 유형의 수, `유형만연결` 건수, `06.레시피명`을 비워 둔 건수도 짧게 표시한다.
3. 명칭 교정·단위 문맥보완·포장 환산 건수, 단위/수량 미상·기준인원 상충·미귀속 메모 건수, 메인 지정 식단 수와 미지정 식단 수/주요 사유를 간단히 요약한다. 실제 수행한 저장 후 재검증 여부도 짧게 밝힌다. 확인하지 않은 검증을 통과했다고 쓰지 않는다.
4. `06.레시피명`이 빈 행의 구성 일치/기본 레시피 연결, 기본단위 대체, B파일에만 보존되는 상세 근거 등 실제 사용에 필요한 한계만 명시한다. 현재 지원하는 레시피명 저장·이름 기준 연결·메인 메뉴 표시를 미지원이라고 안내하지 않는다.

검증표·샘플 승인·사전 승인·단계별 질문으로 응답을 대체하지 않는다. 미확정 항목이 있더라도 처리 가능한 전체 자료를 담은 최종 파일을 생성한다. 전체 처리가 기술적으로 불가능한 경우에만 정확한 완료 범위와 미처리 범위를 밝히며, 일부 결과를 전체 완료라고 표현하지 않는다. 파일 생성 기능이 없으면 동일 헤더의 UTF-8 CSV/JSON으로 실제 내용을 제공하고, 가짜 다운로드 링크를 만들지 않는다.
